Quiero que tomes este mensaje como **feedback directo sobre la implementación actual de Worky** y que trabajes sobre el producto existente, no como si fueras a crear una plataforma nueva desde cero.

Worky ya tiene frontend en React + Vite, backend en Node.js + Express, PostgreSQL con Drizzle ORM, autenticación JWT, bcrypt, roles, changas, perfiles profesionales y mensajería básica.

A partir de ahora quiero que la evolución sea mucho más profesional y consistente entre frontend y backend.

El foco principal es:

**1. Consolidar la arquitectura actual.**

**2. Mejorar profundamente la experiencia del usuario.**

**3. Separar correctamente la experiencia de cliente y Partner sin crear dos plataformas distintas.**

**4. Hacer que todo lo visible en frontend tenga soporte real en backend y base de datos.**

**5. No dejar funciones simuladas o solamente visuales.**

---

# PRINCIPIO GENERAL DE PRODUCTO

Quiero modificar la lógica actual para que Worky funcione más parecido a Mercado Libre en su relación comprador/vendedor.

Cuando una persona entra a Worky, la experiencia por defecto debe ser la de una persona que quiere contratar servicios.

NO quiero que durante el registro inicial tenga que decidir obligatoriamente entre:

* Cliente
* Profesional

Quiero una única cuenta de usuario.

Esa cuenta inicialmente puede:

* Buscar servicios.
* Buscar profesionales.
* Publicar changas.
* Contactar profesionales.
* Contratar.
* Chatear.
* Guardar profesionales.
* Calificar.
* Recomendar.

Y dentro de la misma cuenta debe existir una opción:

**“Ofrecer mis servicios”**

Cuando el usuario selecciona esa opción, comienza el proceso para convertirse en Partner.

El Partner no debe ser una cuenta diferente.

Debe ser una ampliación de la cuenta original.

Una misma persona puede contratar servicios y ofrecer servicios.

# PRIORIDAD TÉCNICA 2 — PERSISTENCIA REAL DE SESIÓN

Quiero solucionar completamente la permanencia de sesión.

Actualmente ya existe JWT, pero quiero que el comportamiento final sea profesional.

## Frontend

Cuando el usuario inicia sesión:

* Mantener correctamente su sesión.
* Recuperar el usuario autenticado cuando se recarga la página.
* No enviar al login cada vez que se refresca la aplicación.
* Mostrar loading mientras se recupera la sesión.
* Mantener información del usuario centralizada.

Crear una arquitectura de autenticación clara.

Por ejemplo:

`AuthProvider`

o solución equivalente.

Debe exponer:

* user
* isAuthenticated
* isLoading
* login()
* logout()
* refreshUser()

No quiero lógica de autenticación repetida en múltiples componentes.

## Backend

Agregar o revisar endpoint:

`GET /api/v1/auth/me`

Debe devolver el usuario autenticado actual.

Nunca devolver:

* passwordHash
* secretos
* información privada innecesaria

Revisar también:

`POST /api/v1/auth/register`

`POST /api/v1/auth/login`

`POST /api/v1/auth/logout`

y, si corresponde por arquitectura:

`POST /api/v1/auth/refresh`

Si se utilizan refresh tokens, implementarlos de manera segura.

No crear una implementación insegura solo para mantener el login.

Antes de comenzar cada etapa:

1. Revisá qué existe.
2. Reutilizá lo que ya funciona.
3. Detectá qué tablas deben cambiar.
4. Creá migraciones.
5. Evitá breaking changes innecesarios.
6. Actualizá frontend y backend de forma coordinada.
7. Typecheck.
8. Build.
9. Tests.
10. Probar recorrido completo.

No quiero funcionalidades visuales sin backend.

No quiero endpoints que no tengan interfaz cuando sean parte de esta etapa.

No quiero duplicar sistemas.

No quiero información ficticia para aparentar que una funcionalidad funciona.

# RESULTADO FINAL ESPERADO

Quiero que Worky evolucione hacia una plataforma donde la experiencia completa sea coherente.

## Usuario

Se registra.

Mantiene su sesión.

Busca.

Publica.

Adjunta fotos/videos.

Habla con profesionales.

Coordina fecha.

Reserva.

Recibe el servicio.

Califica.

Recomienda.

Guarda profesionales.

## Partner

Usa la misma cuenta.

Activa “Ofrecer mis servicios”.

Completa onboarding.

Crea perfil profesional.

Muestra portfolio.

Recibe trabajos compatibles.

Habla con clientes.

Coordina agenda.

Realiza trabajos.

Recibe reviews.

Construye reputación.

Acumula recomendaciones.

Visualiza saldo.

Consulta liquidaciones.

Todo debe estar conectado a datos reales.

La regla a seguir en adelante es:

**si existe en frontend, debe existir realmente en backend; si existe en backend como funcionalidad de usuario, debe tener una experiencia clara y usable en frontend.**

Quiero que trabajes sobre esta implementación como una evolución profesional del producto actual y no como una reconstrucción.
